# STUDIO-S1 — Risk Analysis Package Studio foundation

- Status: implemented; awaiting user review
- Parent boundary: accepted PLATFORM-P6 structural correction
- Branch: `integration/platform-studio-foundation`
- Verification: `make verify-studio-foundation-s1`
- External effects: disabled

## Outcome

Establish the first specialised System Development Studio object without
building every Studio at once. The slice introduces a reusable, versioned
`RiskAnalysisPackageDefinition`, indexes it through the existing Registry and
surfaces its full analytical anatomy in a question-first Studio view.

## Approved definition

The package uses:

- modular composition;
- openly discoverable capabilities with hybrid resolution;
- a stable replayable core plus separately receipted supplemental expansion;
- semantic data roles with default bindings and recorded overrides;
- one package-wide point-in-time temporal envelope;
- an analysis-dossier output boundary;
- deterministic, LLM-assisted and bounded agent-backed implementation kinds;
- optional section briefs with decision-value and research-value admission;
- dual deterministic and agentic publication validation;
- an approval-gated Studio–Codex design/build boundary.

## Visible increment

1. Add Risk Analysis Studio to the object launcher and Studio selector.
2. Show the Daily Portfolio Downside Risk reference package as data roles,
   analytical roles, dossier sections and controls rather than raw hashes.
3. Allow the reviewed source definition to be saved through the existing
   Registry candidate lifecycle.
4. Include the exact package structure in the copyable Studio–Codex build
   brief while keeping executable Codex linkage disabled until PLATFORM-P12.
5. Reuse current return, volatility, drawdown, historical tail-risk, exposure,
   contribution, scenario and report capabilities.

## Reference package

`risk.analysis.daily_portfolio_downside@0.1.0` asks whether volatility,
drawdown, tail losses, concentration and reviewed downside scenarios reveal a
material change in portfolio risk. Historical methods are validated defaults;
future EVT, Monte Carlo, diffusion and regime methods can enter as compatible
substitutions or supplemental analysis without changing the package contract.

## Boundary

- No live LLM call is implied by the agent-backed role declaration.
- No Studio–Codex process, worktree or merge is started from the browser.
- No arbitrary SQL, provider access or financial effect is granted.
- A Registry candidate is saved metadata, not a published or executed package.
- Formal Apply-phase execution remains a PLATFORM-P8 dependency.

## Exit gates

1. The package contract rejects duplicate or unresolved internal roles.
2. Every source, capability, agent and dossier relationship remains inspectable.
3. The source adapter discovers exactly one risk-analysis package and resolves
   its registered capability and agent relationships.
4. The Studio view is compact, responsive and truthfully labels lifecycle and
   future execution boundaries.
5. Focused analytics, Registry, API, architecture and browser checks pass.

## Implementation evidence

- Focused inherited and new gate: 96 tests passed.
- Browser: the question-first reference package rendered its semantic data,
  analytical, dossier and control layers with no console warnings or errors.
- Responsive check: the 700px viewport produced one package column and no
  horizontal overflow.
- Studio–Codex: the generated brief included exact data roles, analytical
  roles, dossier sections, temporal policy and value gate while the executable
  PLATFORM-P12 control remained disabled.
- Apply execution remains honestly deferred to PLATFORM-P8; this slice creates,
  displays and Registry-indexes the reusable package definition.
